# Deployment and rollback procedure

## Current architecture and safeguards

The existing Bytova repository is `Taccountant2026/Bytova`, default/live branch `main`. `CNAME` is `bytova.co.uk`. The source is buildless static output generated by `scripts/build.mjs`, with local fonts and original brand assets. `.github/workflows/preview.yml` can publish GitHub Pages on a push to `main`; its name does not make it a staging deployment. The existing IndexNow workflow also runs on `main`. Do not merge or dispatch either workflow before the owner's publication approval.

All development is isolated on `security/php-response-2026-10-22`. The new security test workflow has read-only content permissions and no deploy job. Existing deployment/DNS/account configuration is not changed.

## Validate the exact candidate

```sh
npm run build
npm run check
npm test
```

In `php-security-audit/`:

```sh
python -m unittest discover -s tests -v
```

No runtime npm packages are required. PDF regeneration requires reportlab; the checked-in PDFs can be used as built. Campaign graphics regeneration uses Pillow, with assets and installed fonts as described by the campaign generator. Those asset-build libraries are not website/CLI runtime dependencies.

For a local review, serve the folder with Python from an authorised workstation:

```sh
python -m http.server 8765 --bind 127.0.0.1
```

Open `http://127.0.0.1:8765/security.html`. Keep the local bind; there is no need to expose a development server to a network. File-URL double-click browsing cannot fetch the JSON dataset and is not a valid checker test.

## Public artifact contents

Keep root public HTML, CSS, JavaScript modules, `robots.txt`, `sitemap.xml`, `CNAME`, verification files and the `assets/` directory together. Downloads and advisory data are inside `assets/security/`, so the existing Pages workflow's `cp -R assets` includes them. The nine new pages and two root modules are included by its existing root-file copy patterns. Source scripts, tests, campaign drafts and the standalone tool folder are source-review materials and do not need to be served as public website content.

## Final owner approval

Approve the exact reviewed commit/PR for the live website, then let the existing Pages process deploy it. Separately approve opening the private utility repository to the public and any public release announcement. Do not treat code approval as permission to send email, submit reports, activate ads or spend money.

Immediately before release:

1. Fetch the current `main` head. If it changed since the candidate base, rebase/merge carefully on the development branch and repeat affected checks; never force-update production.
2. Recheck PHP/GHSA, vendor records and the source-review dates. Rebuild both dataset copies and fixtures if the facts change.
3. Check that the site still retains all three approved bookable services and calendar consent.
4. Retain the pre-merge commit SHA as the rollback point and preserve the currently deployed artifact/version where available.
5. Confirm the owner has reviewed the advisory, optional assistance scope, manually managed email request, analytics notice and campaign destinations.

After approval and deployment:

1. Confirm the existing Pages deployment reports success for the intended commit.
2. Fetch all nine new pages, JSON data, CSS/modules, five PDFs, incident JSON and social image. Require HTTP 200 and correct MIME types. Compare release hashes.
3. Repeat a checker case for unknown, vulnerable, fixed upstream and exact vendor backport. Check wizard progress and downloads at desktop and mobile widths.
4. On a fresh privacy state, verify no Google or statistics requests before consent. Opt in, trigger a synthetic local checker use and inspect a bounded event in the correct GA4 property; do not transmit customer details or create fake leads/bookings. Verify withdrawal.
5. Review the public sitemap and robots file. Use the owner's connected Search Console/Bing tools only where available; if not connected, leave account verification/submission as pending. A successful IndexNow response is only submission receipt.
6. Recheck live status after the next normal monitoring interval and record actual results. Do not invent visitor or protection counts.

## Rollback

If the site release causes a fault, revert the approved merge through an ordinary Git commit and allow the same deployment path to republish the earlier content. Do not reset or force-push `main`. A website rollback is distinct from rolling back a PHP runtime: restoring vulnerable PHP on customer infrastructure is not a safe default. The guide instructs administrators to restrict or take an affected service offline while an authorised specialist agrees a recovery plan.

No backup restore or production rollback has been exercised by this project. The source snapshot, Git history, candidate artifact and documented procedure are preparation, not proof of a tested production restore.
